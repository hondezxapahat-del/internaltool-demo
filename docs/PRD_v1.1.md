# Sinolume 内部分析师配套工具 — PRD v1.1

## Background

这是 Sinolume RAG Demo（`d:\firstclass-demo`，面向客户的问答产品）的配套内部工具，服务对象换成公司自己的政策咨询分析师，而不是外部客户。跟老项目一样，本质是 Working Student – Data and AI Application 岗位的作品集项目，不追求生产级完整度，核心要求是"机制真的能跑、能演示"。

两个项目功能上完全独立，只共享两样东西：一批语料文档（3 份中国科技/政策简报 + 1 份出口管制白皮书），以及网页视觉风格（白底黑字、`#a4161a` 红色点缀，内部工作台调性而非对客营销调性）。

本项目明确要求用 **MCP（Model Context Protocol）** 的方式对外提供核心能力——这是既定决定，不是本 PRD 要讨论的开放问题。

## Problem Statement

Sinolume 的政策咨询师日常会遇到两类"找不到源头"的场景：

1. 同事转来一张报告截图或裁切出来的图表，或者手头有一段文字片段，但不确定这具体出自公司内部哪一份报告——凭记忆或关键词硬猜既慢又容易猜错，图表尤其麻烦，因为图表没有表格那种便于直接检索的行列结构。
2. 要针对某个话题做分析前，想先知道"公司内部之前有没有人分析过这个话题、在哪篇报告里、给出过什么判断"，避免重复劳动、也想在已有分析基础上继续往下做——目前没有直接的办法回答这个问题，只能凭印象翻找。

这两类需求目前都要靠人工翻找报告库解决，效率低、容易遗漏，也没有一个工具能把"这段内容/这张图到底出自哪"这件事直接给出确定或有把握的答案。

## Goals & Non-Goals

### Goals（P0 — 今晚要跑通的最小闭环）

1. 提供一个网页前端（视觉风格对齐老项目），分析师可以在页面上粘贴一段文字。
2. 系统判断这段文字是否出自现有语料库中的某一份具体文档；如果是，明确报出是哪一份；如果不是（比如只是话题相关但并非原文），不能误判成"就是这份文档"。
3. 识别出源文档后，分析师可以在同一前端针对这份文档继续追问，追问的回答严格限定在这份文档内容范围内。
4. 复用现有的 4 份文本语料（3 份简报 + 1 份出口管制白皮书）作为可匹配的文档库。
5. 核心识别能力以 MCP 的方式对外提供，不只是网页表单一条路径（前端与 MCP 之间具体如何共存，留给 TechSpec 决定）。

### Goals（P1 — v1.1 完整目标，今晚不强求，但是这个项目要做到的真实范围）

6. 支持上传图片（报告截图，或从报告里裁切出来的图表），识别出源自哪份内部文档——哪怕两张图表上的文字相同，只要内容、来源或视觉呈现形式不同，也需要能精准区分开，不能仅凭文字相似就误判成同一来源。
7. 当匹配置信度不够时，给出最接近的候选文档列表，而不是强行给一个没把握的判定，也不是简单报"没找到"——但候选也不能是明显不沾边的内容，要保持严谨。
8. 支持"针对某个话题，公司内部谁在哪篇报告里给出过什么分析"这类主题检索，而不只是"确认这段文字/这张图出自哪份文档"这一种单点匹配。
9. 具备用户名+密码登录，且只有白名单内的账号能登录使用，不开放自助注册。

### Non-Goals

1. 不做成通用问答聊天机器人，不追求横向对比 ChatGPT 之类通用大模型的综合能力——定位始终是"精准溯源到具体文档 + 限定范围内追问"，不是全网综合问答。
2. 不做企业级权限体系——白名单登录已经是这个项目里"访问控制"的全部范围，不做角色分级、找回密码等。
3. 不追求支撑任意规模语料库的检索性能，现阶段是 demo 级别的数据量。
4. 不与老项目共享后端、账号体系或功能逻辑，两者完全独立，只共享语料和视觉风格。

## Requirements

### 文字片段溯源（P0）

1. 前端提供一个输入框，供分析师粘贴一段文字。
2. 系统需要明确返回：有没有在语料库里找到匹配文档；找到的话是哪一份；没有足够把握时，不能给出没有依据的判定。
3. 判断"这段文字就是某文档原文"和"这段文字只是话题相关但并非原文"需要有明确、可靠的区分机制，不能把二者混为一谈。
4. 识别出源文档后，追问功能的回答必须严格限定在这一份文档的内容范围内，不能引用语料库里其他文档的信息。
5. 识别出的源文档结果需要在前端清晰、显眼地展示，而不是要分析师自己从追问回答的文字里猜出来。

### 图表/图片溯源（P1）

6. 分析师可以上传一张图片（报告截图，或裁切出的图表）。
7. 系统需要能判断这张图出自哪份文档——即使两张图表文字看起来一样，只要内容、来源或视觉呈现形式不同，也要求精准区分，不能仅凭表面文字相似就误判。
8. 匹配置信度不足时，返回最接近的候选文档列表，而不是单一的强行判定结果；候选列表本身也需要保持相关性，不能什么都往里塞。
9. 图片溯源成功后，同样支持针对该文档的追问，规则与文字片段溯源一致。

### 主题检索（P1）

10. 分析师可以针对一个话题（而非某段具体原文片段）提问，系统能指出语料库中哪些文档涉及这个话题，以及各自给出的分析角度/结论。
11. 这项能力和文字片段溯源共享同一批语料库，但满足的是不同的使用场景（"我手上有片段，帮我找出处" vs "我有个话题，帮我找有没有人分析过、在哪"），两者不能互相替代。

### 账号与访问控制（P1）

12. 需要用户名+密码登录才能使用问答功能。
13. 只有在白名单内的账号才能登录成功，不在名单内的一律拒绝，不提供自助注册入口。

### 前端

14. 需要有网页前端（今晚闭环就要具备，不是靠 MCP 客户端直接对话完成交互）。
15. 视觉风格对齐老项目（白底黑字、`#a4161a` 红色点缀等），但内容和文案基调要体现"内部分析师工作台"，不是对客营销风格。

## Success Metrics

1. **今晚闭环**：粘贴一段确实出自语料库某文档的文字，系统能准确报出具体是哪一份，且结果在前端上清晰可见。
2. **今晚闭环**：粘贴一段话题相关但并非语料库原文的文字，系统不会误判成"就是某份文档"。
3. **今晚闭环**：识别出源文档后发起追问，回答基于该文档内容，且不出现引用语料库其他文档信息的情况。
4. **完整版本**：准备几组"文字相同但来源/内容不同"或"视觉形式不同"的图表测试用例，系统能准确区分，不误判成同一来源。
5. **完整版本**：构造一个匹配置信度明显不够的案例，验证系统给出的是候选列表，而不是强行判定或简单报"没找到"。
6. **完整版本**：白名单外的账号无法登录使用。
7. **完整版本**：前端视觉风格与老项目对比（配色、字体基调等），观感一致。

## Out of Scope

- 图表溯源、候选列表机制、账号白名单登录——这些属于 v1.1 的完整目标（已写入 Goals P1），只是节奏上晚于今晚闭环实现，不是被砍掉。
- 多语言界面切换——老项目 v1.2 已经做过类似方案，但本项目 v1.1 不做，除非之后单独立项。
- 与老项目的功能融合、账号体系共享、后端共享。
- 面向老项目"外部客户"这个角色的任何呈现——本项目定位自始至终是内部分析师工具。

## Open Questions

1. 网页前端与 MCP 两种交互方式之间具体是什么技术关系（前端是否直接调用 MCP 工具，还是两者各自调用同一套核心逻辑）——这是 TechSpec 阶段要解决的问题，不影响本 PRD 的范围界定，但写 TechSpec 时需要优先决定。
2. "主题检索"（Requirement #10）和老项目原有的通用问答能力边界在哪里，会不会显得功能重复——需要在细化需求或 TechSpec 阶段进一步厘清。
3. 图表候选列表机制里"足够接近"具体怎么衡量，目前只有"要保持严谨、不能生搬硬套"这个定性描述，没有可操作的标准。
4. 白名单具体怎么维护（写死几个账号，还是有个配置文件/表），留给 TechSpec 决定。
5. 图表"视觉呈现形式不同"这类要求，需要什么样的测试用例集才能验证做到了"精准区分"，目前还没有具体样例。
